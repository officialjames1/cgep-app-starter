# Acme Health: GRC Engineering Capstone Write-up

## Primary framework

I selected **CMMC Level 2**, built on NIST SP 800-171 Rev 3, as my primary framework.

Three reasons drove this choice. First, CMMC's reliance on NIST 800-171 control families gave the tightest mapping to the policy-as-code and infrastructure controls I had already built in earlier labs, minimizing translation overhead and maximizing reuse — my Rego policies and Terraform overrides map cleanly onto specific, numbered 800-171 requirements (e.g., 03.13.11, 03.01.05) rather than needing to be reinterpreted against a looser set of principles. Second, and more practically, a significant share of the GRC Engineering roles I've seen advertised in the current market explicitly ask for CMMC/NIST 800-171 experience — this capstone was an opportunity to build real, defensible depth in the framework most likely to show up in an actual job requirement, not just the framework that fit the scenario most naturally. Third, I wanted the framework whose controls are the most technical and concrete, with the clearest one-to-one correlation between a control and an actual enforceable configuration — CMMC's granular, engineering-oriented control language (specific KMS/encryption requirements, specific access-control requirements) suits an infrastructure-as-code and policy-as-code system far better than a more principle-based framework would.

I'm treating this as a deliberate trade-off rather than a coincidence: CMMC Level 2 is designed for federal contractors handling Controlled Unclassified Information, and this telehealth company isn't a federal contractor and isn't handling CUI. HIPAA would be the more scenario-native choice for a telehealth PHI system. I chose architectural and career-relevant fit over narrative fit, and I think that's a defensible choice for a capstone meant to demonstrate engineering depth rather than a real compliance filing.

## Design decisions

- **Region:** us-east-1, no particular data-residency requirement for this scenario.
- **Evidence vault Object Lock mode:** GOVERNANCE, 90-day retention. Chosen over COMPLIANCE mode specifically because GOVERNANCE allows a privileged principal to delete objects early if needed — appropriate for a 30-day lab project where I wanted to avoid irreversible lock-in, at the cost of a theoretically weaker chain-of-custody guarantee than COMPLIANCE would provide.
- **Apply on merge vs. manual approval gate:** Apply-on-merge. The pipeline is split into two jobs: `plan-and-gate` runs on every PR and every push (plan + policy gate only, never applies), and `apply-and-sign` runs only on push to `main` — meaning a PR must be reviewed and merged before any real infrastructure change happens. This is closer to continuous deployment than a manual gate, chosen because a single-developer capstone doesn't have a second reviewer to gate on, so the PR-based plan/gate check is the actual review substitute.
- **Single account vs. separate evidence-vault account:** Single AWS account. A separate account for the evidence vault would give stronger isolation (a compromised workload account couldn't tamper with its own audit trail), but added real setup complexity and cost-tracking overhead I judged out of scope for this project's timeline.
- **Terraform vs. policy split:** Every closed gap was addressed in both Terraform (the actual fix) and policy (a Rego rule that fails the plan if the gap is reintroduced) wherever technically feasible — GAP-01, 02, 03, 04, 07, and the enforced half of GAP-08 all follow this pattern. GAP-05 and GAP-06 only have the policy half, by design, since the Terraform half was deliberately deferred.
- **KMS key reuse:** The same customer-managed KMS key (`aws_kms_key.s3`, originally provisioned for the primary/log buckets in `kms.tf`) is reused to encrypt the uploads bucket (GAP-01) and the DynamoDB table (GAP-02), rather than provisioning a dedicated key for each. This means fewer keys and simpler IAM, at the cost of weaker blast-radius isolation between resource types that now share one key.
- **CI/CD deployer role permissions:** The `cgep-grc-gate` role (assumed via GitHub OIDC) is granted `AdministratorAccess` rather than a scoped-down policy. This was a deliberate, documented trade-off given project timeline — the role needs write access to KMS, S3, DynamoDB, Lambda, IAM, CloudTrail, Security Hub, and API Gateway (everything Terraform manages), plus the remote state backend, and hand-writing a precise least-privilege policy covering all of that was judged lower priority than finishing the pipeline itself. Security here is enforced by *who* can assume the role — the OIDC trust condition restricts it to this exact GitHub repository — not by what the role can do once assumed. This is a distinct decision from GAP-07, which scopes the *Lambda's own runtime role* to least privilege; the CI deployer identity and the application's runtime identity are different roles with different trade-offs.

## How the pipeline produces evidence

Tracing one real, complete run end to end (GitHub Actions run `34635289087`, triggered by merging the PR that closed this capstone's demonstration change):

1. **PR opened** against `main` on branch `feature/green-pr-test`. GitHub Actions triggers `plan-and-gate`.
2. **Plan:** the job assumes the `cgep-grc-gate` role via OIDC, runs `terraform init` against the shared S3 remote backend, and produces a plan (`tfplan`) against the real, already-partially-applied infrastructure.
3. **Policy gate:** `scripts/policy-gate.sh` runs `conftest` across all 9 enforced Rego namespaces against `plan.json`. All 9 pass.
4. **PR merged**, triggering a `push` event to `main`. This starts the `apply-and-sign` job.
5. **Apply:** the job re-plans and applies for real — at this point the only changes were the demonstration tweak, since the underlying infrastructure was already fully applied from earlier development.
6. **Bundle + sign:** `plan.json` and `plan.txt` are bundled into `evidence-34635289087-05995e51983ace1cce39d578b54d9bdcc0705a2b.tar.gz`, hashed (SHA-256: `c84af4dd3dfd893b353a353614c508ff051e8a5689f62955437ce39d27009390`), and signed keylessly via Cosign/Sigstore, using the GitHub Actions OIDC identity as the signing identity.
7. **Upload:** the bundle, its hash, and its signature are uploaded to the evidence vault (`acme-health-grc-evidence-vault-bfeaab80`) under `runs/34635289087/`, along with a `receipt.json` recording the S3 object version ID.
8. **Verify:** `scripts/verify-evidence.sh` downloads the bundle back from the vault, recomputes its SHA-256 and confirms it matches, verifies the Cosign signature against the Sigstore transparency log (with the certificate identity pinned to this exact repository and workflow file), and confirms the Object Lock retention date is still in the future. It reports `CHAIN INTACT`.

This is a real signed, verified evidence chain against live AWS infrastructure — not a simulated or mocked run.

## Trade-offs and lessons from remediation

**Scope decision: GAP-05 and GAP-06 deferred.** Closing GAP-05 (placing the Lambda inside the VPC) requires the private subnets to have a route to AWS services — currently they have none. The standard fix is a NAT Gateway, which carries a real ongoing hourly cost, the first resource in this project with genuine per-hour billing rather than flat or negligible cost. Given cost constraints for a 30-day capstone, I chose not to add one. This also meant deferring GAP-06 (reserved concurrency, DLQ, X-Ray), since a DLQ and CloudWatch logging both depend on the same network path a NAT Gateway would provide. Both gaps are documented in OSCAL as accepted risk, with Security Hub monitoring and Lambda's built-in retry behavior as compensating controls. Both Rego policies still exist and pass their unit tests, proving detection works, but are intentionally excluded from the enforced CI gate so they don't block merges on a knowingly-open, deliberately-scoped gap.

**Platform limitation: WAF cannot attach to an HTTP API.** GAP-08 calls for WAF protection on the API Gateway stage. AWS WAFv2's web ACL association explicitly does not support HTTP APIs (`aws_apigatewayv2_*`) — only REST APIs (v1), Application Load Balancers, Cognito User Pools, AppSync, and App Runner. The only ways to add WAF to this stack would be migrating to a REST API or fronting the HTTP API with CloudFront, both out of scope. I closed the achievable two-thirds of GAP-08 (access logging + throttling) in Terraform and documented the WAF gap in OSCAL as an accepted, architecture-driven limitation, with API Gateway's own throttling, CloudWatch access logs, and Security Hub monitoring as compensating controls.

**Discovered dependency: KMS access is required once DynamoDB uses a CMK.** After closing GAP-02 (customer-managed KMS key on the DynamoDB table) and GAP-07 (scoping the Lambda's IAM policy down to exactly the actions `handler.py` performs), the intake API started failing with a 500 error. CloudWatch Logs showed the real cause: DynamoDB's envelope encryption requires the caller to have `kms:Decrypt` and `kms:GenerateDataKey` on the table's CMK — a dependency the original wildcard `dynamodb:*` permission had been silently covering, since AWS-owned default keys don't require explicit KMS grants the way customer-managed keys do. This wasn't visible until both gaps were closed together, and it's a good illustration of why least-privilege IAM work has to be validated against a live, end-to-end test, not just checked against a static policy. Fixed by adding a narrowly-scoped KMS statement (Decrypt + GenerateDataKey, resource-scoped to the single key) to the Lambda's inline policy.

**Infrastructure gap: no remote Terraform state backend, initially.** For most of Layer 1 and 2, Terraform state lived only on my local machine. When I wired the real CI/CD pipeline in Layer 3, `terraform plan` in GitHub Actions started from zero state, and it caught things like a KMS key ARN reading as `(known after apply)` in the CI plan JSON that were real, known values locally. I provisioned a dedicated S3 bucket and DynamoDB lock table, added a `backend "s3"` block to `main.tf`, and ran `terraform init -migrate-state` to move the existing state over without losing it. This is a foundational IaC practice I hadn't needed until multiple environments (my laptop and CI) needed to read the same state.

**CI/CD identity discovery: GitHub's immutable OIDC subject claim format.** My OIDC trust policy initially used the standard, widely-documented pattern `repo:OWNER/REPO:*` for the `sub` condition — and it failed with `Not authorized to perform sts:AssumeRoleWithWebIdentity` even though every other piece of the OIDC configuration (provider, audience, thumbprint) was correct. Decoding the actual JWT GitHub issues revealed the real subject claim: `repo:OWNER@<org-id>/REPO@<repo-id>:ref:...` — GitHub now embeds stable numeric IDs after the org and repo names specifically so trust policies survive renames or ownership transfers. Most tutorials and even some official examples still show the name-only pattern, which silently breaks against this newer format. I found this by adding a temporary debug workflow that decoded and printed the real JWT payload rather than continuing to guess at the trust policy.

**CI/CD IAM discovery: read-only was insufficient once the pipeline needed to write.** The CI role initially had only `ReadOnlyAccess` attached, which worked fine for plan-only runs against local state. Once I added the S3/DynamoDB remote backend and wired a real `apply-and-sign` job, the role needed write access to the lock table, the state bucket, and every resource Terraform manages — `ReadOnlyAccess` failed with an explicit `AccessDeniedException` on `dynamodb:PutItem` against the lock table. I broadened the role to `AdministratorAccess` (see Design decisions above) rather than hand-authoring a precise policy, a deliberate scope trade-off given the project timeline.

**OSCAL discovery: control IDs must satisfy a strict token format, and must match the real published catalog.** My first draft of the OSCAL component and profile used control IDs I'd invented in a plausible-looking but incorrect format (`03.13.11`). `trestle validate` rejected every one of them: OSCAL's `control-id` field uses a token/NCName-style pattern that cannot start with a digit. Beyond the format issue, I had also never actually confirmed what ID strings NIST's real, published SP 800-171 Rev 3 OSCAL catalog uses. Downloading and inspecting the catalog directly showed the real format is `SP_800_171_03.13.11` — letter-prefixed, and specific to how NIST structured this particular OSCAL conversion. Both issues had to be fixed before `trestle validate -a` passed cleanly.

## What I didn't get to

- **GAP-05 (Lambda in the VPC)** — not closed. Requires a NAT Gateway (ongoing hourly cost) to give the private subnets a route to AWS services; scoped out given cost constraints. Detection policy written and tested, not enforced in the CI gate.
- **GAP-06 (reserved concurrency, DLQ, X-Ray)** — not closed, for the same networking-dependency reason as GAP-05. Detection policy written and tested, not enforced in the CI gate.
- **GAP-08, WAF portion** — not closed. AWS WAFv2 cannot attach directly to an HTTP API; would require migrating to a REST API or adding CloudFront, both out of scope. Logging and throttling (the other two-thirds of GAP-08) are closed. Detection policy written and tested, not enforced in the CI gate.
- **Second KMS key for defense-in-depth** — the uploads bucket and DynamoDB table share one CMK with the primary/log buckets rather than each having its own. A dedicated key per resource type would improve blast-radius isolation but adds cost and IAM complexity I didn't think was justified for this scope.
- **Least-privilege CI/CD deployer role** — the `cgep-grc-gate` role has `AdministratorAccess` rather than a precisely scoped policy. A production system would derive this from actual apply activity (e.g., via IAM Access Analyzer policy generation), which I didn't have time to build out here.
- **Separate AWS account for the evidence vault** — currently in the same account as the workload, which is a weaker isolation model than a dedicated account would provide.
